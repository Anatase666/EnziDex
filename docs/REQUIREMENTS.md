## 1. Бизнес-требования

### 1.1. Контекст

Стартап разрабатывает стоматологический гель **«ЭнзиДекс»** на основе фермента **декстраназы**. Механизм действия — ферментативное разрушение полисахаридного матрикса зубной биоплёнки (декстранов, синтезируемых *S. mutans*), что отличает продукт от механических и абразивных решений.

Известные характеристики продукта:

| Параметр | Значение |
|---|---|
| Наименование | ЭнзиДекс / EnziDex |
| Форма выпуска | гель, 10 мл |
| Действующий компонент | декстраназа |
| Позиционирование | не содержит фтора (fluoride-free) |
| Изготовитель | ООО «ЭНЗИДЕКС», РФ, Пермский край |
| Состав (INCI) | вода, сорбитол, глицерин, CMC, ксантановая камедь, лимонная кислота, монофосфат натрия, ментол, бензоат натрия, декстраназа |

- Дисклеймер одной строкой: продукт и его статус `[TODO: заказчик]`.

### FR-G3. Форма заявки (ключевой компонент)

Используется на `/contacts` и в CTA-секциях других страниц как один переиспользуемый компонент.

**Поля:**

| Поле | Тип | Обязательное | Валидация |
|---|---|---|---|
| Имя | text | да | 2–60 символов |
| Телефон | tel | одно из двух | маска `+7 (___) ___-__-__`, допускать зарубежные номера |
| Email | email | одно из двух | RFC-совместимая проверка |
| Тип обращения | select | да | «Я покупатель» / «Я представитель клиники» / «Партнёрство и поставки» / «Другое» |
| Сообщение | textarea | нет | до 1000 символов, счётчик |
| Согласие на обработку ПДн | checkbox | да | ссылка на `/privacy`, отправка заблокирована без галочки |

**Поведение:**
- Валидация на `blur` и перед отправкой; сообщения об ошибке под полем, привязаны через `aria-describedby`.
- Состояния: `idle` → `submitting` (кнопка заблокирована, спиннер) → `success` (форма заменяется сообщением об успехе с указанием срока ответа) / `error` (текст ошибки + предложение написать напрямую на email).
- Защита от повторной отправки и двойного клика.
- Антиспам: honeypot-поле, скрытое от пользователя и от скринридера, + минимальное время заполнения (< 3 с = отклонить).
- Тексты ошибок конкретные: не «Ошибка», а «Не удалось отправить заявку. Напишите нам на {email} — ответим в тот же день».

**Транспорт заявок.** Сайт статический (см. 6.2), серверных обработчиков нет. Выбрать один вариант `[TODO: заказчик]`:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Formspree / Getform** | 5 минут настройки, есть антиспам и уведомления на email | внешний сервис, лимит бесплатного тарифа |
| **B. Telegram Bot API через serverless-функцию** (Vercel/Cloudflare Worker) | заявка мгновенно в чат, бесплатно | нужен отдельный деплой функции, токен в env |
| **C. Google Apps Script → Google Sheets** | заявки в таблицу, бесплатно | ручная настройка, нет уведомлений из коробки |

По умолчанию реализовать **A** с абстракцией: вся логика отправки — в `lib/submitLead.ts` с единым интерфейсом, чтобы смена транспорта затрагивала один файл. Ключи и URL — только через переменные окружения, никогда в коде.

## 5. Контентная модель

Все тексты выносятся из JSX в типизированные файлы. Это обязательное требование: заказчик правит контент без правки вёрстки.

```
/content
  site.ts        # название, дескриптор, контакты, реквизиты, навигация, футер
  home.ts        # секции главной
  product.ts     # состав, преимущества, применение
  science.ts     # механизм, тесты, публикации
  faq.ts         # категории и вопросы
  legal.ts       # реквизиты, маркировка, документы
  seo.ts         # metadata по страницам
```

Пример схемы:

```ts
// content/types.ts
export type Ingredient = {
  inci: string;          // "Dextranase"
  name: string;          // "Декстраназа"
  role: string;          // "Действующий компонент"
  description: string;
  isActive?: boolean;
};

export type Benefit = {
  id: string;
  title: string;

## 6. Технические требования

### 6.1. Стек

- **Next.js** (App Router) + **TypeScript** в strict-режиме.
- **Tailwind CSS**. Дизайн-токены — в `tailwind.config.ts`, не хардкод произвольных hex в компонентах.
- Никаких UI-китов (MUI, Chakra, shadcn) без отдельного согласования — они навязывают чужую визуальную идентичность.
- Шрифты — через `next/font`, локальный хостинг, без запроса к Google Fonts в рантайме.
- Иконки — локальный SVG-набор в `/components/icons`, не подключать целые библиотеки ради 6 иконок.

### 6.2. Режим сборки

Статический экспорт (`output: 'export'`). Следствия, которые нужно учесть заранее:

- Route handlers и серверные экшены недоступны → форма работает через внешний транспорт (FR-G3).
- `next/image` требует `images.unoptimized: true` либо предварительной оптимизации на этапе сборки. Изображения готовятся заранее в WebP/AVIF в нужных размерах.
- Для GitHub Pages — обязательны `basePath` и `assetPrefix`, иначе стили и картинки отвалятся. Вынести в конфиг через env, чтобы локально и на VPS работало без правок.

### 6.3. Структура проекта

```

- `.env.example` в репозитории с перечнем переменных без значений. `.env.local` — в `.gitignore`.

## 7. Дизайн-требования

### 7.1. Направление

Референс из бэклога задаёт визуальную рамку: светлый холодный фон, белые карточки с мягкими тенями, тёмная почти-чёрная кнопка как единственный контрастный акцент, скруглённые углы, много воздуха, гротеск. Это направление принимается. Задача исполнителя — не скопировать макет-заглушку, а довести его до продуктового уровня.

### 7.2. Токены (базовое предложение, уточняется)

```
--bg-page      #EEF3F2   холодный мятно-серый фон
--bg-surface   #FFFFFF   карточки, поля
--ink          #10202A   основной текст, тёмная кнопка
--ink-muted    #5A6B72   подписи, вторичный текст
--accent       #1E7F72   акцент: ферментная зелень, ссылки, иконки
--hairline     #DCE6E4   границы, разделители
```

Акцент — единственный цветной элемент в интерфейсе. Зелёный выбран как отсылка к ферментной/биохимической природе продукта, а не как «медицинский синий» по умолчанию.

### 7.3. Типографика

- Одна гарнитура-гротеск с хорошей кириллицей и широким набором начертаний. Кандидаты: Inter, Manrope, Golos Text, Onest. Финальный выбор — за исполнителем с обоснованием; не брать шрифт «по инерции».
- Единая типографическая шкала, заданная в конфиге. Длина строки основного текста — до 75 символов.
- Заголовки — плотный трекинг, крупный кегль в hero.

### 7.4. Чего не делать

Требования продиктованы тем, что эти приёмы читаются как шаблон:

- Не выделять одно слово в заголовке цветом или курсивом.
- Не ставить над каждым блоком набранный капслоком «эйбрау»-лейбл.
- Не превращать весь контент в одинаковые карточки с одинаковым радиусом и одинаковой серой тенью.
- Не добавлять стрелку «→» в текст каждой кнопки.
- Не ставить нумерацию 01 / 02 / 03 там, где содержимое не является последовательностью. Нумерация уместна только в разделе «Как использовать».
- Не анимировать появление каждой секции при скролле. Допустим один осмысленный анимированный момент — например, схема механизма действия. Всё остальное движение — только в ответ на действие пользователя.

### 7.5. Сетка и адаптив

- Контейнер: максимальная ширина 1200px, боковые поля 24px (мобильный) / 40px (десктоп).
- Брейкпоинты: 360, 768, 1024, 1440.
- Проверка обязательна на 360px — самый частый источник переполнений.

## 8. Нефункциональные требования

### 8.1. Производительность
- Lighthouse mobile Performance ≥ 90; LCP < 2.5 с; CLS < 0.1.

- `alt` у всех содержательных изображений; декоративные — `alt=""`.
- Уважение `prefers-reduced-motion`.
- Поля формы связаны с `<label>`, ошибки озвучиваются через `role="alert"`.

### 8.3. SEO
- Уникальные `title` и `description` на каждой странице.
- Open Graph и Twitter Card, OG-изображение 1200×630.

Chrome, Firefox, Safari, Edge — последние две версии; iOS Safari и Chrome Android. Проверяются: раскладка, шрифты, формы, поведение sticky-хедера.

- Только HTTPS, редирект с HTTP.
